# Research: Coolify environment variables, secrets, and Docker build args for Compose resources

**Scope:** Hyllan is deployed today via a bare `docker compose --profile production` stack (`compose.yaml`, `Dockerfile`, `.env.example`, README's "Production deployment" section) — five services (`db`, `auth`, `app`, `proxy`, `backup`), all runtime secrets as plain Compose `environment:`/`.env` values, and one build-time-only value, `NEXT_PUBLIC_GLITCHTIP_DSN`, passed as a Docker build `ARG` because Next.js inlines `NEXT_PUBLIC_*` vars into the client bundle at build time, not at container start (see `Dockerfile`'s `ARG NEXT_PUBLIC_GLITCHTIP_DSN` / `ENV NEXT_PUBLIC_GLITCHTIP_DSN=$NEXT_PUBLIC_GLITCHTIP_DSN` in the `builder` stage, and `compose.yaml`'s `app.build.args`). The repo owner wants to add Coolify — a self-hosted PaaS already running on the target Hetzner VPS — as a second, parallel deployment path for this same Compose file. This note researches, against Coolify's own official docs (docs.coolify.io / coolify.io/docs), how Coolify injects env vars and secrets into a Docker-Compose-based resource at runtime, and specifically whether/how it can satisfy `NEXT_PUBLIC_GLITCHTIP_DSN`'s build-arg requirement.

---

## 1. Recommendations (summary)

| Question | Recommendation |
|---|---|
| Which Coolify resource type | Deploy via an **Application** resource with the **Docker Compose** build pack, pointed at the Hyllan git repo (`Docker Compose Location: compose.yaml`) — not the git-less "Service Stack" (paste-a-compose-file) resource type, whose build-arg support is undocumented (see §3). |
| Runtime secrets (`DATABASE_URL`, `GOTRUE_JWT_SECRET`, `POSTGRES_PASSWORD`, etc.) | Coolify auto-detects every `${VARIABLE}` reference in `compose.yaml` and surfaces each as an editable field in the resource's Environment Variables tab (Normal or Developer/`.env`-paste view). Fill these in there; leave each variable's default **Runtime Variable = on**, and turn **Build Variable off** for pure-runtime secrets that no service builds against, since Compose build variables are written into a shared build-time `--env-file` that all buildable services can read from. |
| `NEXT_PUBLIC_GLITCHTIP_DSN` as a build ARG | **Supported, but only documented for the Docker-Compose *build pack* under Applications**, not confirmed for Service Stack resources. Add it as an environment variable in the Coolify UI, toggle **Build Variable on** / **Runtime Variable off** (it's build-only). Coolify passes Build Variables to `docker compose build` via a generated `--env-file`, and Hyllan's existing `compose.yaml` (`build.args: NEXT_PUBLIC_GLITCHTIP_DSN: ${NEXT_PUBLIC_GLITCHTIP_DSN:-}`) already does the Compose-native interpolation needed to turn that into a real build arg — no compose.yaml change needed. |
| Coolify's automatic "Inject Build Args to Dockerfile" toggle | **Turn it off** for this resource. Hyllan's Dockerfile already declares `ARG NEXT_PUBLIC_GLITCHTIP_DSN` by hand inside the multi-stage `builder` stage; Coolify's auto-injection (which historically spliced `ARG` lines only after the *first* `FROM`, breaking multi-stage Dockerfiles — GitHub #7118, fixed but recent) is redundant here and adds risk for no benefit. |
| Multi-service gotcha: secret isolation | **Significant, currently-open gap.** Per an acknowledged (Feb 2026) maintainer response on GitHub, Coolify v4 writes *one* shared runtime `.env` for the whole Compose project and wires it into **every** container via `env_file:` — so `db`, `auth`, `app`, `proxy`, and `backup` would each be able to read every other service's secrets (Postgres password, GoTrue JWT secret, rclone remote credentials, etc.). This is not mentioned in the official docs; flagged here as a real caveat, not fixed until a planned v5. |
| Multi-service gotcha: custom `networks:` | Not applicable to Hyllan today (no top-level `networks:` block in `compose.yaml`) — but if one is ever added, official docs carry a hard **WARNING**: custom networks cause intermittent unreachability over HTTPS because Traefik only sits on Coolify's own managed network. |
| Multi-service gotcha: `profiles:` | **Documented gap.** Official docs never mention Compose `profiles:` at all, and an open GitHub issue reports Coolify mis-preprocesses `--profile`-gated services (merging/duplicating profiles). Hyllan's whole production/dev split (`profiles: ["production"]` on `app`, `proxy`, `backup`) rests on profiles — treat this as unverified and likely to need a Coolify-specific compose variant (e.g. drop `profiles:` for the Coolify path) rather than assuming it will just work. |
| Multi-service gotcha: published `ports:` | `db`'s and `auth`'s host port publishes (`${POSTGRES_PORT}:5432`, `${GOTRUE_PORT}:9999`) bypass Coolify's proxy entirely per the docs' own warning that `ports:` mappings are "outside the control of any proxy configuration" — worth reconsidering for a Coolify-deployed variant of the compose file, since Coolify's Traefik-based domain routing is meant to be the only public entry point. |
| `env_file: .env` (the `backup` service) | **Undocumented.** Official docs don't discuss the `env_file:` directive at all. Secondary reports (GitHub) say Coolify overwrites/replaces custom `env_file` paths with its own generated `.env`, which would break the `backup` service's current pattern of passing through arbitrary operator-supplied `RCLONE_CONFIG_<REMOTE>_*` variables — verify this hands-on before relying on it. |

Detail and sourcing for each below.

## 2. Coolify's model for defining env vars per service

Coolify's [Environment Variables](https://coolify.io/docs/knowledge-base/environment-variables) doc is the canonical reference and applies across resource types. Two editing modes exist: **Normal view**, "individual form card[s]" with "editable key and value fields, along with checkboxes for options like `Build Variable`, `Multiline`, and `Literal`," and **Developer view**, "a plain-text editor where all environment variables are displayed in `.env` file format (`KEY=VALUE`, one per line)," useful for "bulk editing or pasting variables from an existing `.env` file." Saving in Developer view re-parses the whole block; lines starting with `#` are treated as comments. ([Coolify: Environment Variables](https://coolify.io/docs/knowledge-base/environment-variables))

For a **Docker Compose**-based resource specifically, Coolify does not give you a blank slate to declare arbitrary variables — the [Docker Compose knowledge-base page](https://coolify.io/docs/knowledge-base/docker/compose) states plainly: "In all cases the Docker Compose (`docker-compose.y[a]ml`) file is the single source of truth. This means various settings you would normally configure in the Coolify UI (like environment variables, storage, etc.) need to be defined in the compose file itself." Concretely, Coolify scans the compose file text and reacts to three patterns: a hardcoded value ("gets passed to the container but will not be visible in Coolify's UI"), a bare `${SOME_VARIABLE}` reference (creates an editable, uninitialized field in the UI), and a defaulted `${OTHER_NAME:-hello}` reference (creates a prefilled, editable field). Docker Compose's own `:?`-required syntax is also honored: "Required variables (`{VAR:?}`) appear first in the environment variables list and show a red border when empty," and deployment fails if they're left empty. ([Coolify: Docker Compose](https://coolify.io/docs/knowledge-base/docker/compose))

This maps directly onto Hyllan's `compose.yaml`: every runtime secret it needs (`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `GOTRUE_DB_PASSWORD`, `GOTRUE_JWT_SECRET`, `GOTRUE_SITE_URL`, `GOTRUE_API_EXTERNAL_URL`, `DOMAIN`, `AUTH_DOMAIN`, `BACKUP_RCLONE_REMOTE`, etc.) is already referenced via `${VARIABLE}` interpolation in the committed compose file, so Coolify's UI would surface each as an individually editable field the moment the compose file is loaded as an Application's build pack — no compose.yaml changes needed to make them configurable, only values need to be supplied through Coolify's Environment Variables tab. ([Coolify: Docker Compose](https://coolify.io/docs/knowledge-base/docker/compose))

Beyond per-service variables, Coolify also supports three tiers of **shared variables** — Team (`{{team.NODE_ENV}}`), Project (`{{project.NODE_ENV}}`), and Environment (`{{environment.NODE_ENV}}`) — settable once and referenced from any resource, plus **Magic Environment Variables** unique to Compose/Service-Stack deployments: `SERVICE_URL_<ID>`, `SERVICE_FQDN_<ID>`, `SERVICE_PASSWORD_<ID>`, `SERVICE_BASE64_<ID>`, etc., which auto-generate (and persist across redeploys) values like random passwords or FQDNs, addressable from within the compose file. ([Coolify: Environment Variables](https://coolify.io/docs/knowledge-base/environment-variables))

## 3. Build-time ARGs: does Coolify support them for Compose resources?

**Yes — but the supporting documentation lives specifically under the git-based "Application" resource type using the Docker Compose *build pack*, and every independent variable carries two flags, not a single build/runtime switch:** "Every environment variable has two independent flags that control **when** it is available: **Build Variable** and **Runtime Variable**. Both are enabled by default." ([Coolify: Environment Variables](https://coolify.io/docs/knowledge-base/environment-variables))

Crucially, the *mechanism* differs by build pack. The same doc states: "Build variables are injected during image construction. For **Dockerfile** deployments, they are added as `ARG` instructions. For **Docker Compose** and **Nixpacks/Buildpack** deployments, they are passed via `--env-file`. ... Build-time variables are stored in a separate file (`/artifacts/build-time.env`) outside the Docker build context, so they are not included in the final image." ([Coolify: Environment Variables](https://coolify.io/docs/knowledge-base/environment-variables)) In other words, for a Compose-based Application, a Build Variable does not become a literal `ARG` line by itself — Coolify hands it to `docker compose build` as an env-file-backed shell variable, and it is standard Docker Compose variable interpolation (in the compose file's own `build.args:` block) that turns it into an actual build arg passed into the Dockerfile. Hyllan's `compose.yaml` already has exactly this shape:

```yaml
app:
  build:
    args:
      # Must be a build arg, not a runtime env var — see Dockerfile.
      NEXT_PUBLIC_GLITCHTIP_DSN: ${NEXT_PUBLIC_GLITCHTIP_DSN:-}
```

— so marking `NEXT_PUBLIC_GLITCHTIP_DSN` as a Build Variable in Coolify's UI should be sufficient to populate it via this existing interpolation, without any compose.yaml edits. This inference (docs describe the `--env-file` half; ordinary Compose `${VAR}` interpolation in `build.args:` is standard Docker Compose behavior, not something Coolify's docs walk through end-to-end) is corroborated by a secondary source — a blog post specifically about Coolify + Compose + build args — which states the same pattern and adds the caution: "Don't use Build Variable for build args when using Docker Compose [assuming it behaves like the Dockerfile build pack] — they [may] not work [the same way]." ([Cryszon: Environment variables and build args for Docker Compose in Coolify](https://cryszon.github.io/posts/environment-variables-and-build-args-for-docker-compose-in-coolify/) — secondary, blog, used only as corroboration, not as primary evidence)

Separately and additively, the **Docker Compose build pack's own doc** (under `/applications/build-packs/docker-compose`, i.e. specifically for a git-sourced Application using Compose as its build pack) documents a second, independent mechanism — automatic Dockerfile mutation:

> "When building images with Docker Compose, Coolify can inject build arguments into your build process. You can configure these settings in the **Advanced** menu of your application.
> #### Inject Build Args to Dockerfile
> Controls whether Coolify automatically injects build arguments during the build. Disable this in the Advanced menu if you want full control over build arguments in your Dockerfile.
> - **Enabled (default):** Coolify automatically injects build arguments
> - **Disabled:** You manage `ARG` statements yourself in the Dockerfile"

([Coolify: Docker Compose Build Packs](https://coolify.io/docs/applications/build-packs/docker-compose))

This is worded almost identically to the plain **Dockerfile build pack**'s own "Build Arguments" section (same toggle, same wording: "By default, Coolify injects Docker build arguments (`ARG` statements) into your Dockerfile. If you prefer to manage build arguments manually in your Dockerfile, you can disable this behavior in the Advanced menu.") ([Coolify: Dockerfile Build Pack](https://coolify.io/docs/applications/build-packs/dockerfile)) — i.e. Coolify's default behavior is to *also* auto-insert `ARG` lines into the Dockerfile text itself for any configured Build Variable, on top of the `--env-file` mechanism above.

**Recommendation for Hyllan specifically: disable "Inject Build Args to Dockerfile."** Hyllan's Dockerfile already declares `ARG NEXT_PUBLIC_GLITCHTIP_DSN` explicitly inside its `builder` stage (one of three stages: `deps` → `builder` → `runner`), exactly matching the "you manage `ARG` statements yourself" case the toggle is designed for. Leaving auto-injection on is redundant, and there is a concrete historical reason to avoid it for a multi-stage Dockerfile: a closed GitHub bug (secondary source, not docs) reported that Coolify's auto-injection "always inserts build arguments at line 2, assuming the Dockerfile starts with a `FROM` instruction," which breaks both Dockerfiles with leading comments and — directly relevant to Hyllan's three-stage Dockerfile — **multi-stage builds**, since "arguments only become available in the first stage, not subsequent stages with multiple `FROM` instructions." ([GitHub: coollabsio/coolify #7118 — "Build arguments added incorrectly to Dockerfile," closed, fixed via PRs #7123/#7130](https://github.com/coollabsio/coolify/issues/7118) — secondary, GitHub issue, cited only as corroborating context for why manual `ARG` control is the safer choice here, not as authoritative Coolify behavior going forward since it's since been patched).

**Documented gap:** neither the Docker Compose build-pack doc nor the environment-variables doc says whether "Inject Build Args to Dockerfile" / the Build-Variable-via-`--env-file` mechanism applies **per-service** (i.e., only to `app`, which has a `build:` block, leaving `db`/`auth`/`proxy`, which use prebuilt images, untouched) or is applied compose-project-wide. Both doc pages describe the feature only in the singular ("your Dockerfile"), which reads as if it assumes one buildable service per compose project — Hyllan's compose file has two services with a `build:` block (`app` and `backup`). This should be verified hands-on rather than assumed.

**Also unverified — Service Stack resources:** all of the above build-arg documentation lives under `/applications/build-packs/*` — i.e., it documents the git-sourced **Application** resource type using Docker Compose as a build pack. Coolify separately offers a git-less **Service** resource ("Service Stack"), where you paste a compose file directly rather than pointing at a repo (this is how the one-click marketplace services work internally). No official doc page was found describing whether the Build Variable / "Inject Build Args to Dockerfile" mechanism exists identically for this resource type. **Recommendation: use the Application + Docker Compose build pack path for Hyllan** (it's git-sourced anyway, matching how Hyllan's compose.yaml already lives in the repo), rather than the Service Stack path, specifically because build-arg behavior is only confirmed in official docs for the former.

## 4. Gotchas specific to multi-service Compose resources

### 4.1 Shared secrets across all containers in the project (undocumented in official docs; significant, currently open)

The clearest, most consequential gap found: Coolify writes **one** runtime `.env` file per Compose *project*, not per service, and wires it into every container. This is stated in the environment-variables doc itself in passing — "After the build completes, Coolify writes a `.env` file containing all runtime-enabled variables, which is loaded by Docker Compose via the `env_file` directive at container start" ([Coolify: Environment Variables](https://coolify.io/docs/knowledge-base/environment-variables)) — but the doc does not spell out the security implication of "all runtime-enabled variables" landing in every service's container. That implication is spelled out in an open GitHub issue (secondary source, not docs): "[Improvement]: Do not share all environment variables across all containers in a Compose project" (#7655, opened December 2025), reporting that "a single `.env` file is created containing ALL environment variables from the entire Docker Compose project" and is "automatically added to every container's `env_file:` directive" — meaning "any container in a multi-container Docker Compose project can read the secrets/credentials of every other container." A Coolify core-team member acknowledged (February 2026) that this is "a security issue that should be fixed" but said it "cannot be properly addressed in v4," with per-container `.env` isolation planned for a future v5. ([GitHub: coollabsio/coolify #7655](https://github.com/coollabsio/coolify/issues/7655) — secondary, open GitHub issue with a maintainer acknowledgment, flagged clearly as non-doc-page evidence since it is not covered in official docs at all)

**Concrete implication for Hyllan:** deployed as a single Coolify Compose resource, `db`, `auth`, `app`, `proxy`, and `backup` would currently all share one `.env` — so the `backup` container (which needs `POSTGRES_PASSWORD` and rclone remote credentials) would also have visibility into `GOTRUE_JWT_SECRET`, and the `proxy` (Caddy) container would have visibility into `DATABASE_URL`, etc. This is a real reduction in blast-radius containment versus the current bare-Compose deployment (where each service's `environment:`/`env_file:` block is genuinely scoped to that service only). Worth flagging explicitly as a trade-off of the Coolify path versus the existing plain-Compose path, not something to silently accept.

### 4.2 Custom `networks:` blocks (documented, hard warning)

Coolify's Docker Compose build-pack doc carries an explicit `WARNING`-type callout: "If your `docker-compose.yml` defines custom networks, **remove them**. Defining custom networks causes intermittent outages where your app becomes unreachable over HTTPS." The mechanism: Coolify auto-creates an isolated bridge network per resource and connects its own Traefik proxy only to that network; a custom `networks:` block puts containers on two networks simultaneously, and "Traefik is only on the Coolify-managed network, but non-deterministically picks which network IP to route to" — if it picks the wrong one, requests hang or 504. The doc links three corroborating GitHub issues (#4483, #6215, #6153) and recommends simply deleting all `networks:` sections, relying on Coolify's auto-created network for inter-service communication. ([Coolify: Docker Compose Build Packs](https://coolify.io/docs/applications/build-packs/docker-compose)) Hyllan's current `compose.yaml` has no top-level `networks:` block today, so this doesn't block a Coolify deploy as-is, but it does mean **don't add one** if the compose file is ever adapted further for this path.

### 4.3 `profiles:` (undocumented in official docs; reported broken)

Official docs contain no mention of Docker Compose `profiles:` or `COMPOSE_PROFILES` anywhere in the Environment Variables or Docker Compose knowledge-base pages, nor in either build-pack doc. This silence itself is a finding: Coolify's docs never confirm profile-gated services are a supported pattern. A secondary source (open GitHub issue, unresolved) reports that deploying with a custom build command using `--profile` causes Coolify to "mangle the YAML structure" during its preprocessing step — merging multiple declared profiles together and duplicating services rather than selecting the one requested, alongside unrelated variable-escaping corruption. The reporter's own workaround was to abandon profiles and split into separate compose files per environment. ([GitHub: coollabsio/coolify #6395 — "Coolify does not respect docker compose profiles," open, no maintainer response](https://github.com/coollabsio/coolify/issues/6395) — secondary, open/unconfirmed GitHub issue)

**Concrete implication for Hyllan:** the entire dev/production split in `compose.yaml` is expressed via `profiles: ["production"]` on `app`, `proxy`, and `backup` (with `db`/`auth` always active, so `npm run dev` unaffected locally). If Coolify does not reliably honor `profiles:`, a Coolify-targeted deploy of this exact file risks bringing up an unintended subset of services (or all of them, uncontrolled) — this needs hands-on verification before relying on the existing single compose.yaml for both the bare-Compose and Coolify paths; a Coolify-specific compose variant without `profiles:` (all five services unconditional) may be the safer route.

### 4.4 Published `ports:` bypass the proxy (documented)

The Docker Compose knowledge-base page warns generally about `ports:` mappings: "if you use the same Docker Compose file for development and deployment, this may expose the ports of private services that you did not intend," because a mapped port is "available on your server at port [N], outside the control of any proxy configuration." The doc's recommended pattern for genuinely private/internal services is to omit `ports:` and any assigned domain entirely, relying on the isolated project network for service-to-service communication. ([Coolify: Docker Compose](https://coolify.io/docs/knowledge-base/docker/compose))

**Concrete implication for Hyllan:** `db` publishes `${POSTGRES_PORT}:5432` and `auth` publishes `${GOTRUE_PORT}:9999` directly to the host — both are meant to be internal-only, and these publishes exist in the current bare-Compose setup for local host-level convenience/inspection. Deployed via Coolify onto a public-facing VPS, these same lines would expose Postgres and GoTrue directly to the internet, sitting outside whatever protection Coolify's Traefik/domain routing provides for `app`. Worth reconsidering (or firewalling, or making conditional) for a Coolify-targeted variant of the compose file.

### 4.5 `env_file:` directive (undocumented; reportedly overwritten)

Neither official doc page discusses the Compose `env_file:` directive as authored in a user's compose file (as opposed to the `.env` file Coolify itself writes and injects). Secondary reports (uncorroborated by any official doc) say Coolify replaces custom `env_file:` paths with its own generated `.env`, which caused at least one user difficulty running two services that needed distinct, non-overlapping environment files. ([GitHub: coollabsio/coolify discussion #2270 — "Dealing with Docker compose based deployments and .env files," opened May 2024, no maintainer resolution found as of the last visible comment (April 2025)](https://github.com/coollabsio/coolify/discussions/2270) — secondary, unresolved GitHub discussion)

**Concrete implication for Hyllan:** the `backup` service's `env_file: .env` line exists specifically to pass through arbitrary operator-supplied `RCLONE_CONFIG_<REMOTE>_*` variables (whose names aren't known in advance, so they can't be listed individually in `compose.yaml`'s `environment:` block). If Coolify overwrites or ignores this directive, that passthrough mechanism may not work unmodified under Coolify — this specific point needs hands-on verification, not just doc-reading, since official docs are silent on it entirely.
