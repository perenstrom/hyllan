# Research: Can GoTrue act as (or front) an OAuth 2.1 authorization server for MCP clients?

**Ticket:** [PER-282 — Can GoTrue act as (or front) an OAuth 2.1 authorization server for MCP clients?](https://linear.app/per-enstrom/issue/PER-282/can-gotrue-act-as-or-front-an-oauth-21-authorization-server-for-mcp) (child of PER-281, "MCP server for Hyllan")

**Scope:** Hyllan runs standalone GoTrue (self-hosted Supabase Auth, no Kong, JWT-based sessions — see `README.md` and `src/lib/supabase/`) and wants to build a remote HTTP MCP server so chat clients can act as a specific customer/household. This note is pure fact-finding against primary sources for four sub-questions: (a) does GoTrue natively act as an OAuth 2.1 authorization-code + PKCE provider, (b) does it support Dynamic Client Registration (RFC 7591), (c) what documented "AS shim in front of an existing IdP" patterns exist, and (d) what does the current MCP Authorization spec require. **No design recommendation is made here** — this is groundwork for a later design session.

**A note on access:** several primary-source domains (`modelcontextprotocol.io`, `supabase.com`, `www.rfc-editor.org`, `datatracker.ietf.org`, `workos.com`) are blocked by this environment's network egress policy. Where that happened, the same canonical text was retrieved from the spec/project's own GitHub source repository (e.g. `raw.githubusercontent.com` mirrors of the `.mdx`/`.mdx` files that publish to `modelcontextprotocol.io` and `supabase.com`) or via search-tool-mediated direct quotes of the blocked page. Citations below link to the canonical/official URL in all cases; where content was actually pulled from a GitHub mirror of that same page, both URLs are given.

---

## Summary of findings

| Question | Finding |
|---|---|
| a. GoTrue as native OAuth 2.1 AS provider | **Yes.** GoTrue (`supabase/auth`) ships a distinct "OAuth 2.1 Server" feature — its own authorization-code + PKCE issuer, separate from (and the opposite direction of) its social-login "consume a third-party OAuth provider" code. Confirmed in GoTrue's own route table and its official docs. Currently marketed as beta, and self-hosted (non-platform) behavior isn't explicitly documented. |
| b. Dynamic Client Registration (RFC 7591) | **Yes, present**, via `POST /oauth/clients/register` → `OAuthServerClientDynamicRegister`, but **disabled by default** (`allow_dynamic_registration = false`). Supabase's own marketing copy names MCP clients as the reason it exists. |
| c. Documented "AS shim in front of existing IdP" pattern | **Yes**, multiple citable examples: the official MCP TypeScript SDK ships `ProxyOAuthServerProvider` ("Implements an OAuth server that proxies requests to another OAuth server"); WorkOS AuthKit and Auth0 both publish vendor docs describing "our service is the AS, your existing login system stays the login system" integration patterns. RFC 8693 (Token Exchange) is a related but **not equivalent** mechanism — flagged separately below. |
| d. MCP Authorization spec requirements | RS/AS split confirmed. RFC 9728 (Protected Resource Metadata) and RFC 8414 (AS Metadata) are **MUST**. PKCE (RFC 7636, S256) and Resource Indicators (RFC 8707) are **MUST**. RFC 7591 (DCR)'s status **changed materially across spec revisions** — SHOULD in 2025-06-18, downgraded to MAY/"backwards compatibility" by 2025-11-25, and explicitly called "deprecated" in favor of an IETF *draft* (Client ID Metadata Documents) by 2026-07-28. This is flagged explicitly, not papered over, in §5 below. |

Detail and sourcing for each below.

## 1. GoTrue as an OAuth 2.1 authorization-server *provider* (authorization-code + PKCE)

**Distinguishing the two directions, up front:** GoTrue has always supported being an OAuth 2.0 *consumer/client* — the `/authorize` and `/callback` endpoints that redirect a user to Google/GitHub/etc. for "Login with X" social sign-in. That is the *opposite* direction from what PER-282 asks. A generic pass over GoTrue's public GitHub README/marketing copy surfaces only this consumer-side functionality and nothing about issuing tokens to third parties — that is exactly the confusion this ticket warned about, and it is worth calling out explicitly because it is what a shallow pass over the repo (or an out-of-date summary of it) will report.

**What the actual current source and docs show:** GoTrue does separately ship a genuine OAuth 2.1 authorization-server *provider* implementation — a distinct "OAuth 2.1 Server" (a.k.a. "OAuth Server Mode") feature, living in its own package, `internal/api/oauthserver/` (`authorize.go`, `client_auth.go`, `server.go`, `service.go`, `handlers.go`, plus tests) ([`supabase/auth` — `internal/api/oauthserver`](https://github.com/supabase/auth/tree/master/internal/api/oauthserver)). The route table registered in `internal/api/api.go` includes, alongside the existing social-login consumer routes:

| Method | Path | Handler |
|---|---|---|
| GET | `/.well-known/jwks.json` | `api.WellKnownJwks` |
| GET | `/.well-known/openid-configuration` | `api.WellKnownOpenID` |
| GET | `/.well-known/oauth-authorization-server` | `api.WellKnownOpenID` |
| GET | `/oauth/authorize` | `api.oauthServer.OAuthServerAuthorize` |
| POST | `/oauth/token` | `api.oauthServer.OAuthToken` |
| POST | `/oauth/clients/register` | `api.oauthServer.OAuthServerClientDynamicRegister` |
| GET | `/oauth/userinfo` | `api.oauthServer.OAuthUserInfo` |
| GET / POST | `/oauth/authorizations/{authorization_id}[/consent]` | `api.oauthServer.OAuthServerGetAuthorization` / `OAuthServerConsent` |
| GET / DELETE | `/user/oauth/grants` | `api.oauthServer.UserListOAuthGrants` / `UserRevokeOAuthGrant` |
| POST / GET / PUT / DELETE | `/admin/oauth/clients[/{client_id}...]` | `api.oauthServer.AdminOAuthServerClientRegister` / `OAuthServerClientList` / `...Get` / `...Update` / `...Delete` / `...RegenerateSecret` |

(source: [`supabase/auth` — `internal/api/api.go`](https://github.com/supabase/auth/blob/master/internal/api/api.go))

Supabase's own official docs (fetched via the GitHub source of the docs site, since `supabase.com` itself is unreachable from this environment — canonical published URLs are given, with the GitHub source mirror as the verified fetch) confirm this is a real authorization-code + PKCE issuer, not just scaffolding:

- "Supabase Auth functions as an OAuth 2.1 and OpenID Connect identity provider, allowing external applications to authenticate through your Supabase project — similar to 'Sign in with Google' functionality," and explicitly lists **"AI agent authentication via Model Context Protocol (MCP)"** as one of the intended use cases, alongside "Sign in with [Your App]" for third-party developers, first-party mobile/desktop token issuance, and enterprise SSO. It states the implementation is "the OAuth 2.1 authorization code flow with PKCE (Proof Key for Code Exchange)," with tokens as standard Supabase JWTs carrying `user_id`, `role`, and `client_id` claims that respect existing RLS policies. (published: [Supabase Docs — OAuth 2.1 Server](https://supabase.com/docs/guides/auth/oauth-server); source verified: [`supabase/supabase` — `oauth-server.mdx`](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/auth/oauth-server.mdx))
- The flows doc confirms only two grant types are supported — `authorization_code` (with PKCE) and `refresh_token` — and explicitly states "Other grant types like `client_credentials` or `password` are not supported." Authorization codes are "valid 10 minutes, single-use." Supported scopes are `openid`, `email`, `profile`, `phone` (default `email`; `openid` triggers an ID token). (published: [Supabase Docs — OAuth 2.1 Flows](https://supabase.com/docs/guides/auth/oauth-server/oauth-flows); source verified: [`supabase/supabase` — `oauth-server/oauth-flows.mdx`](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/auth/oauth-server/oauth-flows.mdx))
- The getting-started doc frames configuration through `supabase/config.toml` (`[auth.oauth_server]`, `enabled`, `authorization_url_path`, `allow_dynamic_registration`) in the context of the Supabase CLI/local dev and hosted platform, notes redirect URIs require exact matches with mandatory HTTPS in production, and that asymmetric JWT signing (RS256/ES256) is **required** for OIDC ID tokens (HS256 fails). (published: [Supabase Docs — Getting Started with OAuth 2.1 Server](https://supabase.com/docs/guides/auth/oauth-server/getting-started); source verified: [`supabase/supabase` — `oauth-server/getting-started.mdx`](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/auth/oauth-server/getting-started.mdx))

**Maturity/timeline:** GoTrue's own `CHANGELOG.md` dates this feature's rollout across late 2025: `v2.178.0` (2025-08-05, initial OAuth 2.1 server endpoints), `v2.179.0` (2025-08-28, OAuth2 client support), `v2.180.0` (2025-09-23, OAuth client type + authorization endpoint), `v2.181.0` (2025-10-31, authorization list/revoke), `v2.182.0` (2025-11-05, `/oauth/token`), `v2.183.0` (2025-11-20, OIDC integration) ([`supabase/auth` — `CHANGELOG.md`](https://github.com/supabase/auth/blob/master/CHANGELOG.md)). Relative to today's date (2026-08-17), the feature is roughly nine to twelve months old — recent, actively developed, and Supabase's own docs describe it as "currently in beta and free during that period."

**Open gap found (self-hosting applicability):** none of the docs fetched explicitly confirm this feature behaves identically on **standalone/self-hosted GoTrue** (Hyllan's deployment shape — no Kong, direct `GOTRUE_*` env vars, no Supabase CLI/platform) versus the Supabase-managed platform or `supabase start` local dev. The `config.toml` keys documented (`auth.oauth_server.*`) match GoTrue's usual pattern of `config.toml` keys mapping 1:1 to `GOTRUE_*` environment variables (as Hyllan already relies on for its other GoTrue config), and a real `GOTRUE_OAUTH_SERVER_AUTHORIZATION_PATH` environment variable is referenced in a live GitHub issue (see below), which is evidence the feature is env-var-configurable outside the CLI/platform tooling — but this repo's research did not find an explicit primary-source statement confirming full self-hosted parity. Flagging as unresolved rather than assuming.

**Evidence the feature is real but operationally unfinished:** [`supabase/auth` issue #2408](https://github.com/supabase/auth/issues/2408) reports that on hosted Supabase projects, the authorization-code flow's `GET /oauth/authorize` redirects to `{SITE_URL}/oauth/consent`, a path GoTrue itself does not serve (it's a headless API — the consent UI is meant to be built by the operator) and that the Supabase Dashboard doesn't expose the `GOTRUE_OAUTH_SERVER_AUTHORIZATION_PATH` env var to redirect to a custom consent UI. The issue names an "Internal ChatGPT MCP Connector requiring branded UI" as the reported use case, and a fix (PR #2417) was in flight at time of writing. This corroborates that the protocol-level flow (authorize → consent → code → token, PKCE) genuinely works, but that **a consent UI is not shipped by GoTrue/Supabase by default** — any adopter (including a self-hosted deployment) needs to build that page themselves, consistent with the getting-started doc's "The authorization UI must be built by developers; Supabase provides the OAuth endpoints only."

## 2. Dynamic Client Registration (RFC 7591)

**What RFC 7591 requires, per the RFC itself:** the registration endpoint "MUST accept HTTP POST messages with request parameters encoded in the entity body using the `application/json` content type," returns a `client_id` (REQUIRED) and optionally a `client_secret`, and clients using redirect-based flows "MUST register their redirection URI values" as part of the metadata payload; "[u]se of an initial access token is required when the authorization server limits the parties that can register a client." ([RFC 7591 — OAuth 2.0 Dynamic Client Registration Protocol](https://www.rfc-editor.org/rfc/rfc7591); text quoted here was retrieved via search-tool-mediated direct quotation since `rfc-editor.org` is blocked in this environment — see the access note above. Mirror: [datatracker.ietf.org/doc/html/rfc7591](https://datatracker.ietf.org/doc/html/rfc7591))

**GoTrue's support:** the route table in §1 shows a dedicated, unauthenticated `POST /oauth/clients/register` mapped to `api.oauthServer.OAuthServerClientDynamicRegister` — a handler name that directly matches RFC 7591's shape (client self-registers, gets back a `client_id`), distinct from the authenticated admin-only client-management endpoints (`/admin/oauth/clients/*`, which is manual/operator-driven registration). ([`supabase/auth` — `internal/api/api.go`](https://github.com/supabase/auth/blob/master/internal/api/api.go))

Supabase's own docs name **the exact use case this ticket is about**: the `oauth-server.mdx` overview lists "Dynamic client registration for MCP clients" as one of the feature's headline standards-support bullets, directly alongside "OAuth 2.1 with mandatory PKCE" and "JWKS endpoint for token validation." ([`supabase/supabase` — `oauth-server.mdx`](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/auth/oauth-server.mdx))

**But it's off by default and only lightly documented beyond that:** the getting-started guide's example `config.toml` shows `allow_dynamic_registration = false` as the baseline, with dynamic registration called out as "Optional: enable dynamic client registration" — i.e., present, toggleable, but not the default posture. ([`supabase/supabase` — `oauth-server/getting-started.mdx`](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/auth/oauth-server/getting-started.mdx)) The oauth-flows doc, which covers the authorization-code/PKCE/token/scopes mechanics in detail, does not itself describe the registration request/response shape (RFC 7591 fields supported, whether an initial access token is required, rate limits, etc.) — this repo's research did not find that level of documentation in the sources fetched. That's a genuine documentation gap worth flagging rather than assuming either way (e.g., whether self-hosted GoTrue's DCR endpoint is open-registration or gated).

## 3. Documented "AS shim in front of an existing IdP" pattern

If a deployment needed (or chose) to *not* rely on GoTrue's native OAuth 2.1 Server feature directly, the following are documented, citable examples of a small OAuth 2.1 AS shim sitting in front of an existing session/credential backend and issuing its own tokens after validating that backend — found per the ticket's request for **real, citable** examples only.

**Official MCP SDK reference implementation:** the official MCP TypeScript SDK ships a class built for exactly this shape. `ProxyOAuthServerProvider` (`packages/server-legacy/src/auth/providers/proxyProvider.ts`) implements the SDK's `OAuthServerProvider` interface with the explicit stated purpose: **"Implements an OAuth server that proxies requests to another OAuth server."** Its authorize handling documents that "[t]he proxy redirects the browser to the upstream AS's authorize endpoint with `redirect_uri = params.redirectUri`, so the upstream — not this proxy — issues the callback," and it deliberately reports `authorizationResponseIssParameterSupported = false` because it cannot honestly assert its own issuer identity for tokens actually minted upstream. ([`modelcontextprotocol/typescript-sdk` — `proxyProvider.ts`](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/server-legacy/src/auth/providers/proxyProvider.ts)) **Currency caveat:** in the SDK's current monorepo layout this class lives under the `server-legacy` package; this research did not find an equivalent proxy-provider class yet in the newer `server` package, so its status going forward (still the recommended pattern vs. being phased out) is unclear from the source alone and worth re-checking before relying on it in a design.

**Vendor-documented patterns describing the same shape (AS-as-a-service, existing login stays the login system):**
- **WorkOS AuthKit** documents this directly for MCP: "For MCP, AuthKit is your authorization server — your MCP server just verifies the tokens it issues," while "[y]our application authenticates users using your existing authentication system," then "calls AuthKit's completion API to complete the OAuth flow" so "AuthKit handles the OAuth consent, token issuance, and returns control to the MCP client." Token verification on the MCP server side works the same way regardless of which login system authenticated the user. ([WorkOS Docs — Model Context Protocol (AuthKit)](https://workos.com/docs/authkit/mcp); content retrieved via search-tool-mediated quotation since `workos.com` is blocked in this environment)
- **Auth0** documents configuring Auth0 as the authorization server in front of an MCP server, including enabling "OIDC Dynamic Application Registration," and describes being able to "front existing identity providers through Auth0 as your authorization server" (their worked example fronts Google login specifically, i.e. a third-party social IdP rather than a self-hosted session backend, but the structural pattern — Auth0 issues MCP-facing tokens, something else handles the actual login — is the same shape). ([Auth0 Docs — Authorization for MCP Server](https://auth0.com/ai/docs/mcp/get-started/authorization-for-your-mcp-server), [Auth0 Docs — Auth0 MCP Server](https://auth0.com/docs/get-started/auth0-mcp-server))

**A related-but-not-equivalent mechanism worth naming explicitly:** RFC 8693 (OAuth 2.0 Token Exchange) defines a `grant_type=urn:ietf:params:oauth:grant-type:token-exchange` request that lets an authorization server act as a Security Token Service, exchanging one token (`subject_token`) for another, typically with a different audience — e.g. a resource server swapping an inbound client-audience token for a new token scoped to a downstream API it needs to call on the user's behalf. ([RFC 8693 — OAuth 2.0 Token Exchange](https://www.rfc-editor.org/rfc/rfc8693); content corroborated via search-tool-mediated quotation, `rfc-editor.org` blocked in this environment) This is a real, RFC-documented mechanism, but it solves a **different** problem than "front an existing session backend with a new AS" — it's about a server (already acting as an AS or RS) minting a *second*, differently-scoped token for a *downstream* call, not about validating an existing non-OAuth session/credential and minting an MCP-facing authorization code for a *client*. This research did not find an official/vendor primary source describing RFC 8693 as *the* mechanism for the "shim in front of an existing IdP" scenario this ticket asks about — it surfaced only in secondary blog/vendor-marketing content discussing broader MCP gateway architectures, which falls outside this ticket's primary-sources-only scope. Naming it here only so its actual, narrower scope is on record rather than conflating it with the shim pattern.

## 4. Current MCP Authorization specification requirements

The MCP specification repository (canonical publish target `modelcontextprotocol.io`, unreachable from this environment — verified instead via the specification's own GitHub source, which is the same Markdown that renders to the docs site) contains multiple dated revisions: `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25`, and `2026-07-28` (plus an in-progress `draft`) ([`modelcontextprotocol/modelcontextprotocol` — `docs/specification`](https://github.com/modelcontextprotocol/modelcontextprotocol/tree/main/docs/specification)). Findings below are drawn from the `2025-06-18` revision (the ticket's named baseline) and the `2026-07-28` revision (the most recent dated revision found in the repository as of this research, 2026-08-17), with `2025-11-25` used to pin down when specific changes happened.

**Roles (all revisions, consistent):** "MCP Server (Resource Server)" acts as "an OAuth 2.1 resource server, accepting protected resource requests using access tokens"; "MCP Client" acts as "an OAuth 2.1 client, making protected resource requests on behalf of a resource owner"; "Authorization Server" "[i]nteracts with users and issues access tokens for MCP servers," with implementation details "beyond this specification's scope," and "may be hosted with or separately from the resource server." ([MCP Specification — Authorization, `2026-07-28`](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization); source: [`.../2026-07-28/basic/authorization/index.mdx`](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/index.mdx))

**RFC 9728 (Protected Resource Metadata) — MUST, both revisions checked:** "MCP servers **MUST** implement OAuth 2.0 Protected Resource Metadata" and include an `authorization_servers` field naming at least one authorization server; on an unauthenticated request, servers "**MUST** use the HTTP header `WWW-Authenticate`" to point at the resource metadata document per RFC 9728 §5.1. Servers must implement at least one discovery mechanism (`WWW-Authenticate` header and/or well-known URI per RFC 9728's patterns); clients must support both and fall back to the well-known URI construction when no header is present. ([MCP Specification — Authorization Server Discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery); source: [`.../authorization-server-discovery.mdx`](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/authorization-server-discovery.mdx))

**RFC 8414 (Authorization Server Metadata) — MUST, client side:** clients "MUST follow the OAuth 2.0 Authorization Server Metadata [RFC8414]" to learn how to interact with the AS, trying multiple well-known endpoints in priority order (OAuth 2.0 with path insertion, OIDC with path insertion, OIDC path appending) per RFC 8414 §3.1 and §5, and must validate that the fetched metadata's `issuer` matches the issuer identifier used to build the well-known URL. (same sources as above)

**RFC 7591 (Dynamic Client Registration) — status changed materially across revisions, flagged explicitly rather than smoothed over:**
- `2025-06-18` (the ticket's named baseline): "MCP clients and authorization servers **SHOULD** support the OAuth 2.0 Dynamic Client Registration Protocol [RFC7591] to allow MCP clients to obtain OAuth client IDs without user interaction," explicitly framed around MCP's problem that clients "cannot know all possible MCP servers and their authorization servers in advance." Servers that don't support it are told to fall back to hardcoded client credentials or a user-facing manual registration UI. ([MCP Specification — Authorization, `2025-06-18`](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization); source: [`.../2025-06-18/basic/authorization.mdx`](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-06-18/basic/authorization.mdx))
- `2025-11-25`: a **new, competing mechanism** — OAuth Client ID Metadata Documents (an IETF *draft*, not an RFC) — is introduced as the preferred option: "MCP clients and authorization servers **SHOULD** support OAuth Client ID Metadata Documents as specified in [draft-ietf-oauth-client-id-metadata-document-00]." RFC 7591 is downgraded to: "MCP clients and authorization servers **MAY** support the OAuth 2.0 Dynamic Client Registration Protocol [RFC7591] ... This option is included for backwards compatibility with earlier versions of the MCP authorization spec." (source: [`.../2025-11-25/basic/authorization.mdx`](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/basic/authorization.mdx))
- `2026-07-28` (most recent found): RFC 7591 is now described outright as **"deprecated"**: "Dynamic Client Registration is deprecated. New implementations should use Client ID Metadata Documents instead. This option remains available for backwards compatibility." Three registration mechanisms are listed in priority order: (1) Client ID Metadata Documents (primary recommendation — "addresses the common MCP scenario where servers and clients have no pre-existing relationship"), (2) pre-registration (static/hardcoded or user-entered credentials), (3) DCR, kept "for backwards compatibility with authorization servers that do not support Client ID Metadata Documents." ([MCP Specification — Client Registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration); source: [`.../client-registration.mdx`](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/client-registration.mdx))
- The Client ID Metadata Document mechanism itself is **not yet an RFC** — it is an active IETF OAuth Working Group Internet-Draft (`draft-ietf-oauth-client-id-metadata-document`, authored by Aaron Parecki (Okta) and Emelia Smith, at revision `-01` as of March 2026 per the datatracker history), i.e. it is normative within MCP's own spec but not yet a ratified IETF standard in its own right. ([IETF Datatracker — draft-ietf-oauth-client-id-metadata-document](https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/))
- **This directly bears on GoTrue's DCR implementation (§2):** GoTrue's `/oauth/clients/register` endpoint is RFC-7591-shaped DCR — which the newest MCP spec revision now treats as a deprecated/backwards-compatibility-only path rather than the recommended registration mechanism, while still keeping it normatively valid ("MAY"/"remains available"). Whether GoTrue's DCR endpoint alone is sufficient for the current spec, or whether a design would additionally need to account for Client ID Metadata Document support, is exactly the kind of question this ticket's later design session would need to resolve — flagged here as a fact, not a recommendation.

**PKCE (RFC 7636) — MUST, unchanged across revisions:** clients "MUST implement PKCE according to OAuth 2.1 Section 7.5.2," must use the `S256` code challenge method "when technically capable," must check the AS's metadata for `code_challenge_methods_supported`, and "MUST refuse to proceed" if that field is absent. (2026-07-28: [MCP Specification — Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations); source: [`.../security-considerations.mdx`](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/security-considerations.mdx). 2025-06-18 states the same MUST for PKCE per OAuth 2.1 §7.5.2.)

**Resource Indicators (RFC 8707) — MUST, unchanged across revisions:** "MCP clients **MUST** implement Resource Indicators for OAuth 2.0 as defined in [RFC8707] to explicitly specify the target resource," in both the authorization and token requests, using the canonical server URI per RFC 8707 §2 (e.g. `https://mcp.example.com/mcp` is valid; a bare hostname with no scheme, or a URI with a fragment, is not); MCP servers "MUST validate that access tokens were issued specifically for them as the intended audience, according to [RFC8707] Section 2" and "MUST reject tokens that do not include them in the audience claim." Servers "MUST NOT pass through the token it received from the MCP client" to any upstream API call they make. (same sources as PKCE, above)

**Other RFCs referenced (2026-07-28 revision):** `draft-ietf-oauth-v2-1-13` (the OAuth 2.1 core draft itself — note OAuth 2.1 is also still an Internet-Draft, not a ratified RFC, as of this research), RFC 6750 (Bearer Token Usage — the `Authorization: Bearer <token>` header form, tokens MUST NOT go in the URI query string), RFC 9207 (Authorization Server Issuer Identification — clients "MUST validate authorization responses per RFC 9207 Section 2.4," recording and checking the `iss` parameter before proceeding — this requirement is new relative to `2025-06-18`, which does not mention RFC 9207 in the content fetched), and RFC 3986 (URI Generic Syntax, for the canonical-URI normalization rules used by Resource Indicators). Security requirements also state redirect URIs "MUST be either `localhost` or use HTTPS," and authorization servers "MUST validate exact redirect URIs against pre-registered values." (sources as above)
