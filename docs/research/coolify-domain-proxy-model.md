# Research: Coolify's compose-resource domain/proxy model for multi-service stacks

**Scope:** Hyllan is currently deployed via a bare `docker compose --profile production` stack (`app`, `db`, `auth`, `proxy`/Caddy, `backup`), with Caddy binding host ports 80/443/443-udp directly and doing its own ACME. The repo owner wants a second, parallel deployment path via Coolify, a self-hosted PaaS already running on the target Hetzner VPS, using a single "Docker Compose" resource containing the same multi-service stack. This note researches, against Coolify's own official documentation (`coolify.io/docs` — see note below on `docs.coolify.io`), how Coolify handles per-service public domains, TLS, its own Traefik/Caddy proxy, and persistent volumes for a multi-service Compose resource, so that question can be answered before any compose.yaml/Caddyfile changes are made.

**Note on the docs domain:** the ticket's suggested host, `docs.coolify.io`, does not resolve (`getaddrinfo ENOTFOUND docs.coolify.io` when fetched directly). Coolify's official documentation is hosted at `https://coolify.io/docs/*` — that is the primary source used throughout this note.

## 1. Recommendations (summary)

| Question | Recommendation |
|---|---|
| Per-service domains | Supported. In Coolify's normal (non-"raw") Docker Compose resource flow, Coolify parses the compose file, lists the discovered services, and exposes a per-service **Domains** field in its UI; Coolify auto-generates the underlying Traefik router labels from whatever you enter there — you do not hand-write `traefik.*` labels yourself in this mode. For hyllan: set `app`'s Domains field to `DOMAIN` (its container port is 3000, non-80, so the field takes the form `https://<DOMAIN>:3000`) and `auth`'s Domains field to `AUTH_DOMAIN` (container port 9999, i.e. `https://<AUTH_DOMAIN>:9999`) — the port suffix tells Coolify which container port to route to; it is not appended to the public-facing URL. Hand-written `traefik.*` labels (`traefik.enable=true`, `traefik.http.routers.<name>.rule=Host(...)`) are only required under Coolify's separate "Raw Docker Compose Deployment" mode. |
| Proxy conflict | Yes, real conflict. Coolify ships its own reverse proxy (Traefik by default, Caddy as an experimental alternative, switchable) that expects to own the host's proxy-facing ports, and its own docs show that a compose service publishing a host port directly (`ports: ["3000:3000"]`) makes that service reachable "outside the control of any proxy configuration" — i.e. bypasses Coolify's proxy rather than cooperating with it. No official doc was found describing what happens if a compose service binds 80/443 itself (this is flagged as a documented gap), but a related GitHub bug report (flagged explicitly as not official docs) shows Coolify's own proxy hard-fails to start when port 80 is already held by another process. Hyllan's Caddy service — which binds 80/443/443-udp and does its own ACME — should be dropped (or at minimum stripped of its host port publishes and TLS role) when deployed under Coolify, letting Coolify's own proxy own those ports and terminate TLS for both `app` and `auth` via their Domains fields. |
| TLS/certificates | Automatic Let's Encrypt via Coolify's own proxy, comparable to Caddy today: once you enter an `https://` domain in a resource/service's Domains field, Coolify requests and installs the certificate automatically and renews it before expiry, with no manual certbot step. Underneath, this uses HTTP-01 (port 80) or TLS-ALPN-01 (port 443) challenges by default — so DNS must point at the server and ports 80/443 must be reachable (and not intercepted by a proxying CDN like Cloudflare, unless DNS-01 is used instead). Wildcard certificates and DNS-01 both require extra operator configuration: a supported DNS provider, an API token/key for it, and provider env vars set on the proxy — not needed for hyllan's two ordinary (non-wildcard) domains. No explicit "ACME email" field was found documented in the pages reviewed. |
| Persistent volumes | Plain named-volume Compose syntax is supported as-is: Coolify's docs state storage can be "predefine[d] normally in your compose file." Coolify layers a few *extra, optional* keys (`is_directory: true`, `content: |`) onto **bind-mount** style volume entries specifically to auto-create host directories or seed files at deploy time — these are not required for ordinary named volumes like a Postgres data volume or a backup directory, which can be declared exactly as in vanilla Compose. Separately, Coolify's general persistent-storage UI mechanism (for volumes added outside a hand-written compose file) appends the resource's UUID to volume names to prevent collisions across resources. The docs describe persistent storage as preserving data "between deployments," but no single passage in the pages reviewed spells out redeploy/rebuild persistence as explicitly as vanilla Docker Compose docs do — flagged as a minor gap, though nothing suggests Coolify's compose-native volume handling behaves differently from plain Compose. |

Detail and sourcing for each below.

## 2. Per-service domains within one Docker Compose resource

**How it works, per Coolify's own docs:** Coolify's Docker Compose knowledge-base page describes the parsing step plainly: "Once Coolify loads your compose file, it finds a list of services and allows you to assign a domain [per service]." ([Coolify: Docker Compose](https://coolify.io/docs/knowledge-base/docker/compose)) The mechanism for *how* a domain reaches a given service depends on what container port that service listens on: "Services listening on container port 80 need only a domain assignment (e.g., `http://example.com`). For other ports, specify them in the domain field (e.g., `http://example.com:3000`)" — after which "the proxy then makes the service available on standard [80/443] ports externally." ([Coolify: Docker Compose](https://coolify.io/docs/knowledge-base/docker/compose)) In other words, the port you type into the Domains field designates the *container's* listening port for Traefik to route to; it does not change the public-facing URL, which still resolves over standard 80/443.

This per-service domain assignment is a UI-level field on the resource, not something you hand-author as compose labels in the normal flow — Coolify's domains page confirms domains attach "directly to individual applications and services in Coolify through domain field configuration," supporting comma-separated multiple domains and full `https://host:port` syntax. ([Coolify: Domains](https://coolify.io/docs/knowledge-base/domains)) The domains page does not spell out, in one explicit passage, that two *different services within the same compose resource* can each carry an independent domain — but this is consistent with, and directly implied by, the Docker Compose page's "finds a list of services and allows you to assign a domain" wording, which is describing exactly a multi-service compose file. ([Coolify: Docker Compose](https://coolify.io/docs/knowledge-base/docker/compose))

**What this means concretely for hyllan:** in a Coolify-managed (non-raw) Docker Compose resource containing `app` and `auth` as services, you would not add any TLS/proxy labels to the compose.yaml itself for the normal path. Instead, in Coolify's dashboard:
- `app` service → Domains field: `https://<DOMAIN>:3000` (container port 3000)
- `auth` service → Domains field: `https://<AUTH_DOMAIN>:9999` (container port 9999)

Coolify's Docker Compose page also documents an alternative, lower-level mode — **"Raw Docker Compose Deployment"** — for which Coolify still auto-adds `coolify.managed=true`, `coolify.applicationId=<id>`, and `coolify.type=application` labels, but requires the operator to hand-write the Traefik labels themselves to opt into Coolify's proxy, in this documented shape:

```yaml
labels:
  - traefik.enable=true
  - "traefik.http.routers.<unique_router_name>.rule=Host(`coolify.io`) && PathPrefix(`/`)"
  - traefik.http.routers.<unique_router_name>.entryPoints=http
```

([Coolify: Docker Compose](https://coolify.io/docs/knowledge-base/docker/compose)) Applied per-service for hyllan under this raw mode, the pattern would be two distinct router names/rules, one per service (e.g. `traefik.http.routers.app.rule=Host(`${DOMAIN}`)` and `traefik.http.routers.auth.rule=Host(`${AUTH_DOMAIN}`)`), each with its own `traefik.enable=true`. The docs' example only shows the HTTP entry point and a bare `Host()` rule, without also showing the companion TLS/cert-resolver labels a production HTTPS router normally needs — that additional detail was not found spelled out on this page, another minor gap.

Coolify's domains page additionally documents a `HostRegexp` label convention for catching multiple/dynamic domains on one router — "you can automatically catch multiple domains, by editing the Container Labels of your Application or Service and define a `HostRegexp` rule" — which is not the mechanism hyllan needs (two *fixed*, distinct domains on two *different* services), but confirms Coolify's domain-routing is fundamentally Traefik-label-driven under the hood even when the UI abstracts it away. ([Coolify: Domains](https://coolify.io/docs/knowledge-base/domains))

## 3. Proxy conflict: Coolify's Traefik/Caddy vs. hyllan's own Caddy service

Coolify's own reverse proxy is not optional infrastructure sitting beside your services — it *is* the thing that makes any Coolify-managed domain reachable. Coolify's get-started concepts page describes the proxy as sitting "between your application and users, forwarding requests to the right place," enabling "running multiple applications on a single server without port conflicts" — precisely because Coolify itself owns the shared host ports and fans requests out by domain. ([Coolify: Concepts](https://coolify.io/docs/get-started/concepts)) Coolify's supported-proxy page confirms there are exactly two built-in options — "Coolify supports `Traefik` (default) and `Caddy` (experimental) proxies" — switchable at any time (since beta.237), with resources needing `caddy_*` or `traefik_*` labels present before a switch (added automatically on restart, or via a "Reset to Coolify Default Labels" action). ([Coolify: Supported Proxy](https://coolify.io/docs/knowledge-base/server/proxies)) There is no third option to "bring your own proxy service inside the same host" documented here — the two supported proxies are Coolify-managed instances of Traefik or Caddy, not a slot for an arbitrary user-authored proxy container.

Coolify's firewall/ports documentation lists the ports the platform's own proxy and control plane need open on the host: 80/TCP ("SSL certificate generation via reverse proxy"), 443/TCP (HTTPS traffic — both also used for GitHub webhooks), plus 6001/6002 (realtime/terminal) and 8000 (dashboard, closable once a custom domain + proxy is set up). ([Coolify: Firewall](https://coolify.io/docs/knowledge-base/server/firewall)) Notably, this page does not mention 443/UDP (HTTP/3/QUIC) at all — so there is no documented confirmation that Coolify's Traefik proxy publishes a UDP entry point the way hyllan's Caddy currently does; this is a gap in the docs reviewed, not a confirmed capability or limitation.

**Does Coolify document what happens if a compose service also binds 80/443 directly?** Not explicitly as a "conflict" scenario, but the mechanism is implied by how Coolify documents the *escape hatch* for host port binding: the Docker Compose page's "Service Port Mapping" section states that adding a `ports` attribute (e.g. `"3000:3000"`) publishes that container port directly on the host, and explicitly warns "your service will be available on your server at port 3000, outside the control of any proxy configuration." ([Coolify: Docker Compose](https://coolify.io/docs/knowledge-base/docker/compose)) That is Coolify describing, for arbitrary ports, exactly the situation hyllan's Caddy service creates for 80/443/443-udp: a compose service claiming a host port bypasses Coolify's proxy layer entirely rather than integrating with it. Two containers (Coolify's proxy and hyllan's Caddy) cannot both publish the same host port 80/443 simultaneously under Docker's own port-binding model regardless of platform — this is ordinary Docker behavior, not something specific to Coolify, and no Coolify doc page found states an explicit "if you do this, X happens" for that exact collision.

As corroborating (but **not** official-docs) evidence of Coolify's *own* proxy expecting exclusive ownership of ports 80/443 — flagged explicitly as inferred from Coolify's GitHub issue tracker, not from `coolify.io/docs` — a bug report shows Coolify's proxy start-up logic performing a hard check for port 80 availability and refusing to start with "Port 80 is in use. You must stop the process using this port," even when the proxy itself was reconfigured to use different ports; this was later patched as a regression, but the underlying design intent (a hard check that port 80/443 must be free for Coolify's proxy) is consistent with the official docs' framing of those ports as "reserved" for the platform's own proxy. ([GitHub: coollabsio/coolify issue #6234](https://github.com/coollabsio/coolify/issues/6234) — not an official docs.coolify.io/coolify.io page; cited only as a documented-gap pointer.)

**Conclusion for hyllan:** the Caddy service as currently defined (binding 80, 443, 443/udp, doing its own ACME) is not a supported pattern to run *inside* a Coolify-managed compose resource on the same host where Coolify's own proxy is active — it would compete for the same host ports Coolify's Traefik/Caddy proxy expects to own. It should be dropped from the Coolify variant of the stack (or at minimum have its `ports:` publishes and ACME/TLS directives removed so it no longer touches 80/443), with `app` and `auth` instead exposed via Coolify's per-service Domains fields (§2) and TLS handled by Coolify's own proxy (§4).

## 4. TLS / certificate provisioning

**Automatic, comparable to Caddy today.** Coolify's concepts page states this directly: the proxy "automatically manages SSL/TLS certificates through Let's Encrypt integration. When you specify an `https://` domain, certificates are automatically requested and installed with no manual setup required. Renewal happens automatically before expiration." ([Coolify: Concepts](https://coolify.io/docs/get-started/concepts)) This mirrors what hyllan's Caddy already does today (per the deployment-architecture research doc) — no separate certbot process, no manual cert file management.

**Underlying mechanism and operator requirements:** Coolify's troubleshooting page for failed certificate issuance describes the two default challenge types — HTTP-01 ("Let's Encrypt sends an HTTP request to your server on port 80 with a unique token. If your server responds with the correct token, it confirms domain ownership, and the certificate is issued.") and TLS-ALPN-01 (validated over port 443 during the TLS handshake). ([Coolify: Let's Encrypt Not Generating SSL Certificates](https://coolify.io/docs/troubleshoot/dns-and-domains/lets-encrypt-not-working)) Consequently, the concrete operator requirements documented are: ports 80 and/or 443 open and reachable from the internet; correct DNS A/AAAA records pointing at the server (the doc notes Let's Encrypt may prefer IPv6 if an AAAA record exists, so a misconfigured or absent IPv6 host will break issuance — remove unnecessary AAAA records if IPv6 isn't actually served); and no interfering third-party proxy — the doc specifically calls out that a proxying CDN like Cloudflare can break HTTP validation, advising to "either use a DNS challenge or stop proxying your domain through the third-party service." ([Coolify: Let's Encrypt Not Generating SSL Certificates](https://coolify.io/docs/troubleshoot/dns-and-domains/lets-encrypt-not-working))

**DNS-01 / wildcard path (not needed for hyllan's two plain domains, but documented):** Coolify's DNS challenge page states DNS-01 is required in two cases — wildcard certificates ("these _require_ DNS challenge") and servers without a publicly reachable port 80 (internal network, firewalled, Tailscale-only). ([Coolify: DNS Challenge](https://coolify.io/docs/knowledge-base/proxy/traefik/dns-challenge)) The mechanism: "Traefik asks your DNS provider to create a temporary `TXT` record under `_acme-challenge.<your-domain>`," which requires the domain to be managed by one of lego's supported DNS providers, an API token/key scoped to create/delete DNS records, provider-specific environment variables (examples given: `CF_DNS_API_TOKEN` for Cloudflare, `HETZNER_API_TOKEN` for Hetzner, `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_REGION` for Route 53), and selecting the provider under the server's Proxy settings in Coolify's UI. ([Coolify: DNS Challenge](https://coolify.io/docs/knowledge-base/proxy/traefik/dns-challenge)) The wildcard-certs page shows the corresponding Traefik router labels needed to request a combined apex+wildcard cert (`traefik.http.routers.traefik.tls.domains[0].main=coolify.io` / `...sans=*.coolify.io`), and explains the practical benefit — "Because Traefik does not need to request a new cert for each resource, new deployments become reachable over HTTPS immediately instead of waiting for ACME issuance" — which is a nice-to-have for a fleet of subdomains, not a requirement for hyllan's fixed two-domain setup. ([Coolify: Wildcard SSL Certificates](https://coolify.io/docs/knowledge-base/proxy/traefik/wildcard-certs))

**Gap:** none of the pages reviewed documented an explicit "ACME email address" configuration field/step — Coolify's docs describe DNS and port requirements in detail but the reviewed pages are silent on whether/where an operator sets a Let's Encrypt contact email. Flagged as not found rather than asserted either way.

## 5. Persistent volumes in a Docker Compose resource

**Named-volume syntax works as in vanilla Compose.** Coolify's Docker Compose page states plainly: "You can predefine storage normally in your compose file, but there are a few extra options that you can set to tell Coolify what to do with the storage." ([Coolify: Docker Compose](https://coolify.io/docs/knowledge-base/docker/compose)) The "extra options" documented are both scoped to **bind-mount** style entries specifically, not to ordinary named volumes: `is_directory: true` on a `type: bind` volume entry tells Coolify to create an empty host directory at deploy time ("this is not available in a normal docker-compose"), and `content: |` on a `type: bind` entry lets Coolify materialize a file with (environment-variable-interpolated) content at deploy time — both illustrated with concrete YAML on that page, e.g.:

```yaml
volumes:
  - type: bind
    source: ./srv
    target: /srv
    is_directory: true
```

([Coolify: Docker Compose](https://coolify.io/docs/knowledge-base/docker/compose); example also shown on [Coolify: Docker Compose Build Packs](https://coolify.io/docs/applications/build-packs/docker-compose)) For a plain named volume — the pattern hyllan already uses for `hyllan-db-data:/var/lib/postgresql/data` and `hyllan-backups:/backups` — none of this extra machinery is needed; the ordinary top-level `volumes:` block plus per-service `- name:/path` reference is exactly what "predefine storage normally in your compose file" refers to.

**Separate, general persistent-storage mechanism:** Coolify's dedicated persistent-storage page documents a second layer — the storage UI available on Applications/Services generally — describing two storage kinds under Docker Engine: a `volume` (Docker-managed, named + destination path) or a `bind mount` (host path + destination path, no Docker volume created). ([Coolify: Persistent Storage](https://coolify.io/docs/knowledge-base/persistent-storage)) For the `volume` kind specifically, the docs state Coolify "automatically adds the resource's UUID to the volume name" — "to prevent storage overlapping between resources." ([Coolify: Persistent Storage](https://coolify.io/docs/knowledge-base/persistent-storage)) This UUID-suffixing behavior is documented for storage added through this general UI mechanism; the Docker Compose page's "predefine storage normally in your compose file" wording does not restate whether volumes declared directly in a hand-written compose file also get this UUID treatment or keep the literal name given — the two pages describe what read as two different configuration surfaces (compose-native volume declarations vs. the UI storage feature), and the overlap between them isn't spelled out in one place. Flagged as a minor ambiguity, not load-bearing for hyllan since the named volumes are declared directly in compose.yaml either way.

**Redeploy/rebuild persistence:** the persistent-storage page frames the whole feature as letting you "preserve your data between deployments" ([Coolify: Persistent Storage](https://coolify.io/docs/knowledge-base/persistent-storage)) — consistent with named Docker volumes surviving container recreation the same way they do in plain Compose (a named volume is not deleted by `docker compose up`/rebuild unless explicitly removed with `-v`/`down --volumes`). No page reviewed walks through this guarantee as explicitly, end-to-end, as vanilla Docker Compose's own reference does — flagged as a documentation thinness rather than evidence of different behavior. Also relevant: the Docker Compose page's separate "Custom Compose Overrides" mechanism (`docker-compose.custom.yml`, merged on top of Coolify's own base compose files) is explicitly designed so operator customizations "persist automatically" across Coolify platform upgrades — a related but distinct persistence guarantee (about Coolify's *own* control-plane compose files, not application data volumes). ([Coolify: Custom Compose Overrides](https://coolify.io/docs/knowledge-base/custom-compose-overrides))

**What this means concretely for hyllan:** `db`'s `hyllan-db-data:/var/lib/postgresql/data` and `backup`'s `hyllan-backups:/backups` can be declared with ordinary top-level named-volume syntax in the Coolify-variant compose.yaml, unchanged from today's shape — no `is_directory`/`content` keys needed since these are named volumes, not bind mounts requiring host-side directory/file creation.
