# App skeleton: Next.js App Router, Vitest, Tailwind, npm, Node 24

The previous bare `ts-node` skeleton is replaced entirely with a Next.js (App Router) app under `src/app`, built with npm and pinned to Node 24 (current LTS) via `.nvmrc` and `engines.node`. We chose App Router over Pages Router since it's the actively developed router and the default for new Next.js apps. Styling uses Tailwind CSS, included from the start since it's a common baseline rather than a later migration. Linting is `eslint-config-next` (flat config) only — no extra `typescript-eslint` strictness or import-ordering rules yet, since those are easy to add once real code exists to check. Formatting is Prettier, wired into ESLint only via `eslint-config-prettier` (which turns off ESLint's stylistic rules) rather than running Prettier as an ESLint rule, keeping linting and formatting as two independent, non-conflicting commands. Testing is Vitest, configured upfront for both plain unit tests and React component tests (jsdom environment + React Testing Library), since retrofitting a test environment after components exist is more disruptive than including it now; tests are co-located with source as `*.test.ts`/`*.test.tsx`. We skipped pre-commit hooks (Husky/lint-staged) for now — CI (a GitHub Actions workflow running lint, typecheck, test, and build) catches regressions without adding local commit friction. TypeScript uses Next.js's default `strict: true` with no additional compiler flags, and a `@/*` import alias resolves to `src/*`. `tsconfig.json` strictness and ESLint rule strictness are both treated as easy-to-raise-later floors, not final settings.

**Amended (PER-272):** navigating between authenticated views (e.g. clicking "Edit") was slow, traced to three compounding causes. First, in staging/production every server-side auth check (`src/proxy.ts`'s middleware, plus `getSessionClaims`/`requireSessionClaims` in `src/lib/auth.ts`) requested `${NEXT_PUBLIC_SUPABASE_URL}/auth/v1/...`, and `NEXT_PUBLIC_SUPABASE_URL` is the app's own **public** domain — so the request left the container through Caddy over the public internet and came back in through `next.config.ts`'s `/auth/v1/*` rewrite to reach GoTrue, a full external round trip for what's really a same-network container-to-container call (`app` and `auth` already share a Docker network). Fixed by `src/lib/supabase/internal-fetch.ts`: when the new `GOTRUE_API_INTERNAL_URL` env var is set (`http://auth:9999` in `compose.yaml`/`compose.staging.yaml`/`compose.coolify.yaml`, unset in local dev), a custom `global.fetch` passed to `createServerClient` reroutes only the `/auth/v1/*` request path there directly, stripping the prefix GoTrue doesn't understand itself. The client is still constructed with the public `NEXT_PUBLIC_SUPABASE_URL` — only where the request actually lands changes — so the session cookie's name, which `@supabase/ssr` derives from that URL's hostname by default, stays identical between the browser and server clients; pointing the client itself at the internal URL instead would have silently diverged the two.

Second, each page ran its auth-check → household-lookup → item-lookup as a fully serial chain with no loading UI, so the whole wait rendered as a blank screen. Fixed with a standard `loading.tsx` per top-level authenticated route (`/`, `/items/[id]/edit`, `/items/new`, `/account`), all sharing a minimal `LoadingIndicator` (`src/app/loading-indicator.tsx`); the root route's `loading.tsx` omits the app header since that route serves both signed-in and signed-out content and the signed-out view has none.

Third, `getSessionClaims` is now wrapped in React's `cache()` so multiple callers within a single render pass share one `getClaims()` call rather than each issuing their own — forward-looking hygiene rather than a fix for the proxy/page split, since middleware and the page render are separate invocations `cache()` can't span.

Left deliberately unaddressed: GoTrue is still configured with only a symmetric (HS256) JWT signing secret, so `getClaims()` still can't verify a session locally and still round-trips to GoTrue for every check (now a cheap internal-network call rather than a public one) — migrating to asymmetric signing keys, which would eliminate that round trip entirely, is tracked separately as PER-273 since it's a deployment/secrets change rather than a pure code change.
