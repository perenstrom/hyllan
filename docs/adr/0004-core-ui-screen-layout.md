# Core MVP screens use a dense table list, unit postfixed onto amount, and minimal account access

Three structurally different UI directions were prototyped for the item list, add/edit item, and account screens: a dense operator table, a card grid with a modal add flow, and a mobile-first list with a bottom-sheet/FAB pattern. The dense table direction won on live review, refined further before being locked in.

The item list is a single flat table with three columns: Name, Amount, and Actions. Amount postfixes the unit directly onto the quantity (`2 kg`, `250 g`, plain `6` for the unit-less `count` default) instead of a separate unit column or badge — one scannable number per row rather than two things to cross-reference. The increment/decrement controls live in a dedicated rightmost Actions column as icon buttons, kept separate from the Amount column so that column stays purely informational. Out-of-stock items (quantity 0) stay visible in place rather than being hidden or split into a separate section — every item a household tracks stays visible regardless of stock level.

The table is responsive down to mobile widths: action buttons are sized for touch (32px), and the table sits in a horizontal-scroll container as a fallback for narrow viewports or long item names. Rejected: the card-grid-plus-modal variant added visual overhead for what is fundamentally a scannable list, and the mobile-first FAB/bottom-sheet variant added chrome that turned out not to be necessary once the table variant proved responsive on its own.

**Amended (PER-232):** the four Actions-column icon buttons (decrement, increment, edit, delete) wrap into a 2×2 grid below the small breakpoint instead of staying in a single row. The single-row layout was the main cause of needing horizontal scroll at ordinary phone widths, since it alone accounted for most of the table's minimum width. Horizontal scroll remains as a fallback, but now for genuine edge cases (very long item names) rather than as the primary answer to button overflow.

**Amended (PER-236):** out-of-stock rows are no longer indicated with a visible "Out of stock" text label next to the name. Because quantity updates are optimistic (PER-231), a label that conditionally mounts/unmounts caused an immediate layout shift on click — stacked under the name it grew that row's height at narrow widths, and inline it widened the shared, unfixed-width Name column across every row at wider widths. The label is now always present in the DOM as a screen-reader-only (`sr-only`) node — still announced to assistive tech — while sighted users get a red background tint on the row instead (Tailwind `red-100` light / `red-950` dark), which can't cause a layout shift the way mounting text can. Fixed in the same pass: the row's muted text color, previously `zinc-400` (light) / `zinc-600` (dark), had the shades swapped relative to their backgrounds and failed WCAG AA contrast (2.46:1 light / 2.72:1 dark; needs 4.5:1) against the plain page background. Corrected to `zinc-600` (light) / `zinc-300` (dark), which clears AA against both the plain background and the new red tint. Five tint candidates (current baseline, red, rose, orange, amber) were prototyped with computed contrast ratios before red was chosen; the prototype was a throwaway branch, not merged.

Add/edit item is a focused form (name, quantity, unit) reachable via a "+ Add item" action, rather than inline editing in the table. Account basics are reached via a small avatar-triggered dropdown offering "Sign out" and "Delete account," plus a minimal dedicated account page hosting the same two actions — consistent with [household signup being single-user with no settings to speak of](0002-household-is-single-user-and-cascades-on-deletion.md). Delete account is destructive-styled and sits behind a confirmation dialog stating the deletion is immediate and irreversible, matching the cascade-delete behavior already decided for account deletion.

Typography is locked to Inter, chosen for legibility at small sizes and clean tabular figures, fitting the dense-table direction. (This also fixed a latent bug in the scaffolded app: the CSS theme referenced a `--font-sans` variable that nothing actually set — the loaded Geist font was wired to a differently-named variable — so the app was silently falling back to the browser's default font.)

The full three-variant prototype (all variants, the variant switcher, and the refinements above) is the primary source for this decision and lives on the throwaway branch/PR, not in the main app — see the resolution comment on the originating ticket for the link. This ADR is the durable record of the decision itself; only the decision, not the throwaway prototype code, is part of the MVP spec this map is building toward.

**Amended (PER-237):** the "every item stays visible regardless of stock level" rule above is no longer absolute — households can now toggle hiding out-of-stock (quantity 0) rows entirely from the table. The toggle defaults to off (all items shown, matching the original behavior) and persists to `localStorage`, not a per-household server-side setting; a household record still carries no settings fields of its own. It's an icon-only eye/eye-slash button in the header row next to "+ Add item," sourced from `lucide-react` — the app's first icon library dependency, now coexisting with the hand-rolled inline-SVG icons in `icons.tsx` rather than replacing them. The button carries a custom CSS-only tooltip (`:hover`/`:focus`, no JS state) — the app's first tooltip component — which does not appear on touch, since simulated-hover-on-tap would otherwise turn the button's single tap into a two-tap interaction; the button's `aria-label` still carries the accessible name for screen readers regardless of input method. When the toggle is on and at least one item is hidden, a dismissible pill below the header reads "N out-of-stock item(s) hidden" with an X that clears the filter (equivalent to re-toggling the eye icon); it's suppressed entirely when the hidden count is zero. The pill pulses once whenever the hidden count increases while the filter is already active (e.g. a decrement newly zeroes out an item) — the one case where an item disappears without a direct toggle action — but does not pulse on toggle-on itself, and respects `prefers-reduced-motion`. Rows hidden by the filter vanish instantly on render, consistent with the rest of the table having no transitions.

**Amended (PER-249):** the Name and Amount column headers are clickable to sort the table; Actions never sorts, since it holds buttons rather than data. Sorting is a pure client-side transform over the already-fetched row list (`optimisticItems`) — no new server query or server action — so it composes with the existing hide-out-of-stock filter as just another client-side transform on the same array. Name sorts alphabetically (locale-aware, case-insensitive, matching the existing case-insensitive name-uniqueness rule); Amount sorts by the raw numeric `quantity` only, ignoring unit, since units carry no conversion behavior and so have no meaningful cross-unit order.

Each sortable header cycles through three states on click: ascending → descending → back to the default order (`createdAt` ascending, the table's original order) — only one column is active at a time, and clicking a different column always starts it at ascending regardless of the previous column's direction. Ties (e.g. equal Amount values) fall back to the default `createdAt` order via a stable sort. The active column shows a `lucide-react` sort-direction icon (ascending/descending arrow); headers are rendered as focusable buttons carrying `aria-sort` (`"ascending"`/`"descending"`/`"none"`) for assistive tech.

Sort state persists to `localStorage`, the same mechanism as the hide-out-of-stock toggle (PER-237), rather than resetting on reload. It does not live-reorder rows during an optimistic increment/decrement: the sort order is captured at the moment a header is clicked and stays fixed until the user clicks a header again, so rows don't jump under the cursor while clicking the +/- buttons — consistent with the app's existing bias against jarring optimistic-update side effects (see the out-of-stock label mount/unmount issue above). Splitting the Amount column back into separate Quantity/Unit columns, or any other change to the column set itself, was ruled out of scope for this decision.

**Amended (PER-251):** neither the PER-237 hide-out-of-stock toggle nor the PER-249 column-header sorting described above was ever actually implemented — both amendments above recorded the decision but no build followed, discovered while triaging PER-251. PER-251 folds in building both, for real this time, alongside its own low-stock feature (see [CONTEXT.md](../../CONTEXT.md) for Minimum quantity / Low stock). The PER-249 sorting design is unchanged and now gets built as specified. The PER-237 toggle design is superseded, not built as specified: instead of an eye/eye-slash boolean toggle, the header row gets a "Status" dropdown with three checkboxes — In stock, Low stock, Out of stock — all checked by default (equivalent to the old toggle's off/all-visible default). Unchecking all three is allowed and shows an empty-state message ("No items match the current filter") rather than forcing at least one box checked. The dropdown trigger shows a count only when the filter is non-default (e.g. "Status (2/3)"); the old design's dismissible "N hidden" pill is dropped as unnecessary given the trigger already surfaces filter state. Out-of-stock (quantity exactly zero) and low-stock (below a set minimum quantity, quantity nonzero) are mutually exclusive by construction, so every row falls into exactly one of the three filter buckets, no double-counting or tie-break needed. Low-stock rows get the same tint-plus-`sr-only`-label treatment as out-of-stock (PER-236) but in amber (`amber-100`/`amber-950`) rather than red, contrast-checked against the same WCAG AA bar. Filter state persists to `localStorage` alongside sort state, per the existing precedent.

**Amended (PER-253):** the dedicated account page now hosts a third action beyond "Sign out" and "Delete account" — a change-password form (current password, new password, confirm new password), in its own bordered card below the existing sign-out/delete-account card rather than folded into it. Submitting re-verifies the current password by replaying it through the same sign-in call the login page uses, before calling the auth provider's own password-update method; a wrong current password or a new/confirm mismatch is rejected without changing anything, and any password-strength rejection from the auth provider surfaces verbatim, matching the existing login/signup error handling. The user stays signed in on success — this is a password rotation, not a re-authentication flow, so there's no redirect.
