# Pantry item quantity is tracked per-location, not as a single value, without reopening item identity

Locations (household-managed, e.g. "Pantry", "Garage fridge") let a household see where an item's stock physically sits, not just how much of it exists. Three shapes were considered: (a) location as a single attribute on the item row, which can't represent an item split across two places; (b) folding location into item identity (`household, name, location` unique instead of `household, name`), which reopens ADR 0001's rejection of multiple rows per name and reintroduces the exact quantity-fragmentation it was written to avoid; (c) keeping item identity exactly as ADR 0001 defined it, and moving quantity itself into per-location rows, with the item's total displayed as their sum.

(c) is the decision. A pantry item's identity (`household, name`, case-insensitive, ADR 0001) is unchanged and not reopened by this decision — only where its quantity is *tracked* changes, not what the item *is*. Concretely: an item's quantity lives in one row per `(item, location)` pair (unique — no duplicate rows for the same pairing), plus an implicit unassigned bucket (a null location reference, not a real entity) for quantity not yet assigned anywhere. Increment/decrement acts on a location's row, not on the item's total directly. Deleting a location merges its quantity back into the unassigned bucket rather than discarding it. Locations follow the same case-insensitive per-household name uniqueness as pantry items. `PER-251`'s minimum-quantity/low-stock feature is unaffected: it continues to compare against the item's total (now derived) rather than becoming location-aware.

The exact UI pattern for showing an item's total alongside its per-location breakdown (table row expansion vs. drill-in vs. something else) is deliberately not decided here — see the [Add location support](https://linear.app/per-enstrom/issue/PER-264) wayfinder map.
